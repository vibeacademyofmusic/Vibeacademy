# Security Phase 2 pilot

Active student branch membership is an ACTIVE enrollment whose started_at has arrived and ended_at has not passed, in an ACTIVE class within its start/end dates. Dates use Asia/Ho_Chi_Minh. Null started_at is not active. An active enrollment_pauses interval, future and historical enrollments do not confer current branch membership. default_branch_id is a preference, not authority; academic enrollment is not branch-specific and tuition snapshots must not confer current access. New students without active enrollment remain SUPER_ADMIN-only in this pilot.

BRANCH_ADMIN permissions are mapped to existing role assignments (including global assignments); no user assignment is seeded. Read policies pilot branches, students, classes, schedules, session_occurrences, attendance_records and learning_journals. Only update_student_basic is a new write surface: it changes full_name/preferred_name, checks current membership and cannot change identity, role, branch, enrollment, status or financial fields. Permission names classes.manage, attendance.manage and learning_reports.view are prepared, but their broader mutation/report rollout is deferred. No finance permissions are mapped.

Teacher access requires an ACTIVE account, valid TEACHER assignment, active teacher record and matching operational relationship, never branch membership alone. Current class assignment allows current roster access. Session overrides supersede the primary teacher for session reads. Completed actual-teacher snapshots preserve access to that session/roster; ending class assignment does not erase this historical relationship. Cancelled sessions confer no session access. An independently active class assignment may still confer current roster access. Makeup scope uses explicit participants. Teachers use scoped_students for an allowlisted identity projection; raw student rows remain unavailable to teachers through the new pilot.

Parent helpers require an explicit active student_parents link and active parent account/record/role. Student helper requires own active identity/role. Parent/student portal policies are not opened. Existing feedback and payroll relationship policies are not comprehensively migrated in this pilot; do not interpret these helpers as an app-wide revocation mechanism. Their remaining direct relationship paths need review before any portal rollout.

The restricted staff UI is /operations. Existing /admin entry/actions remain SUPER_ADMIN-only except the separate updateStudentBasic action; this avoids exposing existing admin forms and financial screens to new staff roles. Login routes approved staff roles to /operations. Classes and sessions show at most 100 rows; the pilot is not a complete staff portal.

Helpers use existing enrollment/student/class, class_teacher/teacher, parent-link and session indexes. SECURITY DEFINER helpers have public,pg_temp search paths, authenticated-only execution, and use the caller's auth.uid() rather than caller-provided identities. Definer reads prevent policy recursion. Helpers are STABLE and set-based; production-sized query cost still needs measurement before wider RLS rollout. No speculative indexes were added.

Before Phase 3: agree on paused/historical access and retention, private field access for each role, write permissions for classes/attendance, and measure scoped query plans on realistic volumes. Apply production migration-ledger review separately; this checkpoint authorizes local changes only.
